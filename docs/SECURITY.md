# نموذج الأمان والصلاحيات

يوضّح هذا الملف كيف يحمي المشروع بيانات المتقدمين ولوحة التحكم، وما هي القيود المعروفة التي يجب معالجتها قبل التشغيل الإنتاجي الفعلي.

---

## 1. نطاق الحماية ونموذج التهديد

النظام يتعامل مع ثلاث فئات من البيانات:

| الفئة | أمثلة | مستوى الحساسية |
| --- | --- | --- |
| بيانات عامة | الأقسام، الأخبار المنشورة، نصوص الموقع، الأسئلة الشائعة | عامة |
| بيانات متقدمين | الاسم، الهاتف، البريد، المؤهل، ملاحظات الطلب | شخصية |
| بيانات إدارية | الملاحظات الداخلية، حالة الطلب، جلسات الإدارة | سرية |

التهديدات التي يعالجها التصميم:

- محاولة قراءة أو تعديل بيانات المتقدمين دون تسجيل دخول.
- تخمين كلمة مرور المدير أو إعادة استخدام جلسة مسروقة.
- تزوير طلبات من مواقع أخرى (CSRF) أو تجاوز سياسة المصدر (CORS).
- حقن SQL أو HTML/JavaScript عبر حقول النماذج.
- إغراق نموذج التقديم أو صفحة الدخول بالطلبات.
- حذف بيانات حقيقية بالخطأ عبر أدوات البيانات التجريبية أو إجراء حذف غير مقصود في لوحة التحكم.

خارج النطاق: حماية الجهاز نفسه، أمن الشبكة الداخلية، وهجمات حجب الخدمة الموزعة على مستوى البنية التحتية.

## 2. المصادقة

### كلمات المرور

- تُخزَّن كتجزئة **bcrypt** (عبر `bcryptjs`) مع ملح لكل حساب، ولا تُخزَّن أو تُسجَّل كلمة المرور الصريحة في أي مكان.
- `npm run admin:init` يولّد كلمة مرور قوية ويطبعها **مرة واحدة** إذا لم تُضبط `ADMIN_PASSWORD`، ولا يعيد طباعتها لاحقًا.
- عند محاولة الدخول، تُقارن كلمة المرور مع تجزئة وهمية ثابتة إذا لم يكن الحساب موجودًا، حتى لا يكشف زمن الاستجابة وجود البريد أو اسم المستخدم.
- رسالة الفشل واحدة دائمًا: «بيانات الدخول غير صحيحة»، دون تمييز بين حساب موجود وآخر غير موجود.

### الجلسات

- الجلسات **مخزَّنة على الخادم** في جدول `sessions` داخل SQLite، وليس داخل الكوكي.
- كوكي الجلسة `taiba.sid` يحمل فقط معرف الجلسة، ويُضبط بـ:

| الخاصية | القيمة |
| --- | --- |
| `HttpOnly` | نعم — لا يمكن قراءته من JavaScript |
| `SameSite` | `Lax` |
| `Secure` | نعم في الإنتاج فقط |
| `Path` | `/` |
| `maxAge` | `SESSION_TTL_HOURS` (8 ساعات افتراضيًا) |

- `rolling: true` يجدّد مدة الجلسة مع النشاط.
- عند نجاح الدخول يُنفَّذ `req.session.regenerate()` أولًا لمنع **session fixation**، ثم يُخزَّن معرف المدير في الجلسة الجديدة.
- عند الخروج يُدمَّر السجل من قاعدة البيانات ويُمسح الكوكي.
- الجلسات المنتهية تُحذف تلقائيًا كل 15 دقيقة، وتُرفض عند القراءة إن انتهت صلاحيتها.
- إذا حُذف حساب المدير، تُلغى جلساته القديمة تلقائيًا عند أول طلب (`attachAdmin`).

### حد المحاولات

- `POST /api/auth/login` محمي بـ `express-rate-limit`: **10 محاولات لكل 15 دقيقة** لكل عنوان IP افتراضيًا.
- المحاولات الناجحة تُحتسب أيضًا، لمنع استخدام الدخول الصحيح كغطاء لتخمين حسابات أخرى.
- التجاوز يعيد `429 RATE_LIMITED` برسالة عربية.

## 3. CSRF

يُستخدم نمط **double-submit cookie**:

1. الخادم يُصدر رمزًا عشوائيًا (32 بايت) في كوكي `taiba.csrf` قابل للقراءة من نفس الأصل.
2. كل طلب يغيّر الحالة (`POST`, `PATCH`, `PUT`, `DELETE`) يجب أن يرسل نفس القيمة في الرأس `x-csrf-token`.
3. تُقارن القيمتان بـ `crypto.timingSafeEqual` بعد التحقق من الطول والنمط (`64` حرفًا سداسيًا).
4. الطلبات الآمنة (`GET`, `HEAD`, `OPTIONS`) لا تتطلب الرمز.

لأن المتصفح لا يسمح لموقع آخر بقراءة الكوكي، لا يستطيع المهاجم تزوير الرأس. و`SameSite=Lax` على كوكي الجلسة يضيف طبقة دفاع إضافية.

الرمز مفعّل على:

- `POST /api/applications` (نموذج التقديم العام).
- كل مسارات `/api/admin/*`.
- `POST /api/auth/login` و`POST /api/auth/logout`.

---

## 4. الصلاحيات

- كل مسار تحت `/api/admin` يمر عبر سلسلة ثابتة في `backend/src/routes/admin/index.js`:

```text
requireAdmin  →  requireCsrf  →  validate(schema)  →  route handler
```

- `requireAdmin` تتحقق من وجود `req.admin` المربوط بجلسة صالحة، وليس من أي قيمة يرسلها العميل.
- لا توجد أي واجهة عامة تعيد بيانات المتقدمين أو الملاحظات الإدارية أو تعدّل السجلات.
- صفحات لوحة التحكم (تطبيق React على `/admin/*`) محمية على مستوى الواجهة بإعادة التوجيه إلى تسجيل الدخول، لكن **الحماية الفعلية على الخادم**؛ فتح الصفحة أو تحميل حزمة JavaScript دون جلسة لا يمنح أي وصول للبيانات.
- الحساب الإداري واحد بدور كامل (لا توجد أدوار متعددة في هذه النسخة).

## 5. التحقق من المدخلات

كل كتابة تُتحقق على الخادم باستخدام مخططات **Zod** في `backend/src/validators/schemas.js`، بشكل مستقل تمامًا عن تحقق الواجهة:

- حدود دنيا وعليا لكل حقل نصي، ورسائل عربية لكل خطأ.
- تطبيع النص: إزالة المسافات الزائدة والأحرف التحكمية.
- تطبيع أرقام الهاتف: تحويل الأرقام العربية الهندية إلى لاتينية، وإزالة الفواصل والمسافات، والتحقق من الطول (7–15 رقمًا).
- `slug` يُشتق من الاسم إن تُرك فارغًا، ويُقيَّد بنمط ثابت، مع رفض التكرار (`409 DUPLICATE_SLUG`).
- `image_url` يجب أن يكون مسارًا محليًا يبدأ بـ `/` أو رابط `http(s)://` فقط، وبحد أقصى 500 حرف، مع رفض الروابط النسبية للبروتوكول (`//host`) والشرطة العكسية وأي مسافة.
- `sort_order` عدد صحيح بين 0 و9999.
- الحالة (`status`) تُقبل فقط من قائمة محددة: `NEW`, `UNDER_REVIEW`, `ACCEPTED`, `REJECTED`.
- مفاتيح المحتوى تُرفض إن لم تكن ضمن قائمة بيضاء معرّفة على الخادم.
- التحقق يشمل أيضًا وجود القسم وأنه **منشور ونشط** قبل قبول أي طلب تقديم.

### منع الحقن

- كل استعلامات SQLite تستخدم **استعلامات مُعاملة (parameterized)**، ولا تُدمج أي قيمة من المستخدم في نص الاستعلام.
- البحث النصي يستخدم `LIKE` مع `ESCAPE` لتحييد `%` و`_`.
- كل النصوص الديناميكية في الواجهة تُعرض عبر `textContent` / `createTextNode`، ولا يوجد `innerHTML` لبيانات المستخدم.
- سياسة CSP تمنع أي سكربت أو نمط مضمّن، فلا يوجد مسار لتنفيذ HTML مُخزَّن.
- تصدير CSV يحيّد **CSV/Formula Injection**: أي خلية تبدأ بـ `=` أو `+` أو `-` أو `@` أو tab أو CR تُسبق بفاصلة عليا `'` حتى لا تُنفَّذ كصيغة في Excel أو Google Sheets.

## 6. حدود الطلبات والحد من الإساءة

| الحد | القيمة الافتراضية | المتغير |
| --- | --- | --- |
| حجم JSON | 100 KB | ثابت في `config.limits` |
| حجم نموذج `urlencoded` | 50 KB | ثابت في `config.limits` |
| عدد حقول النموذج | 100 | ثابت في `config.limits` |
| محاولات الدخول | 10 لكل 15 دقيقة | `LOGIN_RATE_LIMIT_MAX` |
| طلبات التقديم | 5 لكل 15 دقيقة | `APPLICATION_RATE_LIMIT_MAX` |
| نافذة الحد | 15 دقيقة | `RATE_LIMIT_WINDOW_MINUTES` |

- الطلبات الأكبر من الحد تعيد `413 PAYLOAD_TOO_LARGE`.
- JSON غير الصالح يعيد `400 INVALID_JSON`.
- منع التكرار في الطلبات: نفس رقم الهاتف + نفس القسم خلال 24 ساعة يعيد `409 DUPLICATE_APPLICATION`، دون كشف رقم الطلب السابق في الرسالة العامة حتى لا يُستدل على طلبات الآخرين.

## 7. رؤوس الأمان والنقل

تُضبط عبر `helmet` في `backend/src/app.js`:

| الرأس | القيمة |
| --- | --- |
| `Content-Security-Policy` | `default-src 'self'; base-uri 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: https:; media-src 'self' https:; font-src 'self'; connect-src 'self'; form-action 'self'; frame-src https://www.youtube-nocookie.com https://www.youtube.com https://player.vimeo.com; frame-ancestors 'none'; object-src 'none'` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `X-Frame-Options` | مقيّد عبر `frame-ancestors 'none'` |
| `Strict-Transport-Security` | مفعّل في الإنتاج فقط |
| `X-Powered-By` | محذوف |
| `Permissions-Policy` | تعطيل الكاميرا والميكروفون والموقع والدفع وUSB وغيرها، مع إبقاء fullscreen لمشغلات الفيديو |
| `Cache-Control` (على `/api`) | `no-store` دائمًا لمنع تخزين بيانات المتقدمين أو حالة الجلسة |

في الإنتاج تُضاف `upgrade-insecure-requests` إلى CSP. لا توجد أي سكربتات أو أنماط مضمّنة في صفحات المشروع، لذلك تعمل السياسة الصارمة دون استثناءات.

في الإنتاج أيضًا تُعاد توجيه أي طلب يصل عبر `http` إلى `https` باستجابة `308`، مع استثناء `/api/health` لفحوص المنصات. هذا ضروري لأن كوكي الجلسة وCSRF مضبوطة `Secure` ولا تُخزَّن على HTTP، ولأن كلمة مرور الإدارة يجب ألا تُرسل نصيًا. يعتمد كشف البروتوكول الأصلي على `req.secure` ثم `X-Forwarded-Proto` عند وجود وكيل عكسي.

يُستخدم `query parser: simple` في Express ليبقى `req.query` مسطحًا، ما يقلّل سطح هجمات تلويث prototype مقارنة بالمحلل الموسّع، مع `parameterLimit` لحد حقول النماذج.

### رفع صور الأخبار

- **النوع:** يُقبل `image/jpeg` و`image/png` و`image/webp` و`image/gif` فقط. **SVG مرفوض** لأنه قد يحمل سكربتات ويُقدَّم من أصل الموقع نفسه.
- **الحجم والعدد:** 5 ميجابايت لكل صورة (قابل للتغيير بـ `NEWS_UPLOAD_MAX_BYTES`)، و6 صور كحد أقصى في الطلب.
- **الأسماء:** تُولَّد على الخادم (`timestamp-random.ext`) ولا يُستخدم اسم العميل أو امتداده، ما يمنع Path Traversal وDouble Extension.
- **فحص المحتوى:** تُفحص **magic bytes** الفعلية للملف (JPEG/PNG/GIF/WebP) بعد الرفع؛ أي ملف يدّعي أنه صورة لكن محتواه ليس صورة حقيقية يُرفض ويُحذف فورًا، وكذلك أي ملفات مؤقتة كُتبت قبل فشل الرفع.
- **التخزين:** داخل `uploads/news/` في جذر المشروع (خارج `frontend/dist` حتى لا يمحوها البناء) ليخدمها `express.static` على `/assets/uploads/news`. يمكن نقلها بـ `NEWS_UPLOADS_DIR`.
- **التنظيف:** عند تحديث الخبر أو حذفه تُحذف ملفات الصور التي لم تبقَ مرجعية في قاعدة البيانات. فشل الحذف لا يُفشل العملية الأساسية.
- **الفيديو:** لا يُرفع أي ملف فيديو؛ تُخزَّن روابط فقط، وتُقيَّد `frame-src` على YouTube وVimeo، ويُستخدم نطاق `youtube-nocookie.com` لتقليل التتبّع.

### CORS

- الأصل نفسه مسموح دائمًا.
- أي أصل آخر يجب إضافته صراحةً إلى `ALLOWED_ORIGINS` (قائمة مفصولة بفواصل).
- لا يُعاد أبدًا `Access-Control-Allow-Origin: *` مع بيانات الاعتماد.
- طلبات `OPTIONS` من أصل غير مسموح تعيد `403`.

### الوكيل العكسي

- `TRUST_PROXY=false` افتراضيًا.
- لا تُفعّلها إلا خلف وكيل عكسي موثوق (Nginx، منصة استضافة)، وإلا أصبح تحديد عنوان IP لحدود المعدل قابلًا للتزوير.

## 8. حماية البيانات والخصوصية

- استجابة إنشاء الطلب العام تعيد **إسقاطًا عامًا** فقط: رقم الطلب، الاسم، القسم، الحالة، التاريخ، ورسالة تأكيد.
- `admin_notes` لا تُعاد أبدًا من أي مسار عام، ولا من قائمة الطلبات الإدارية؛ تُعاد فقط في تفاصيل الطلب داخل لوحة التحكم.
- قائمة الطلبات لا تُضمّن الملاحظات الإدارية افتراضيًا (`includeAdminNotes: false`).
- تصدير CSV إداري فقط، ويتضمن الملاحظات الداخلية لأنه أداة إدارة مقصودة، ويُبنى في الذاكرة دون رابط عام دائم.
- اسم القسم يُحفظ كنسخة (`department_name_snapshot`) داخل الطلب، فلا يتغير تاريخ الطلب عند تعديل القسم لاحقًا.
- البيانات التجريبية موسومة بـ `is_demo = 1` ويمكن تمييزها في كل الواجهات.
- لا تُسجَّل بيانات المتقدمين في سجلات الخادم؛ تُسجَّل آثار الأخطاء غير المتوقعة فقط.

## 9. سياسات الحذف

الإدارة تملك تحكمًا كاملًا في البيانات، بما فيها السجلات الحقيقية. الحذف نهائي ولا يمكن التراجع عنه، لذلك تفرض الواجهة تأكيدًا كتابيًا (كتابة اسم القسم أو عنوان الخبر أو رقم الطلب) قبل تنفيذ أي حذف، ويعيد الخادم `404 NOT_FOUND` عند محاولة حذف سجل غير موجود.

| الكيان | القاعدة |
| --- | --- |
| قسم بلا طلبات | يُحذف نهائيًا بعد تأكيد كتابي في الواجهة |
| قسم له طلبات | يُرفض الحذف بـ `409 DEPARTMENT_HAS_APPLICATIONS` افتراضيًا لحماية الارتباطات؛ ويمكن للإدارة تأكيد الحذف الكامل عبر `DELETE /api/admin/departments/:id?force=true` فيُحذف القسم وطلباته معًا داخل معاملة واحدة |
| طلب حقيقي أو تجريبي | يُحذف نهائيًا من صفحة تفاصيل الطلب أو من قائمة الطلبات بعد تأكيد كتابي برقم الطلب، ويعيد `{ id, reference_number, was_demo }` |
| خبر حقيقي أو تجريبي | يُحذف نهائيًا من محرر الخبر بعد تأكيد كتابي بعنوان الخبر |
| سؤال شائع | يُحذف بعد تأكيد |
| البيانات التجريبية | تُحذف أو تُعاد تهيئتها فقط بعمليات صريحة ورمز تأكيد |

الحذف الكامل للقسم عملية ذرّية: تُنفَّذ داخل `db.transaction()`، فإذا فشل حذف القسم تُلغى عملية حذف طلباته أيضًا. تُسجَّل نتيجة العملية (`deleted_applications`) في الاستجابة، ولا تُحذف أي طلبات تابعة لأقسام أخرى.

عمليات البيانات التجريبية:

- `POST /api/admin/demo-data/seed` — إضافة الناقص فقط، قابلة للتكرار.
- `POST /api/admin/demo-data/reset` — تتطلب `{ "confirm": "RESET_DEMO_DATA" }`.
- `POST /api/admin/demo-data/cleanup` — تتطلب `{ "confirm": "DELETE_DEMO_DATA" }`.

كلها تتطلب جلسة إدارية ورمز CSRF. لا تُنفَّذ تلقائيًا عند تشغيل الخادم، ولا تحذف أي سجل حقيقي. القسم التجريبي المرتبط بطلب حقيقي يُؤرشف بدلًا من حذفه، ثم يُعاد نشره عند `reset`.

## 10. معالجة الأخطاء والسجلات

- كل الأخطاء تعود بالشكل `{ "error": { "code", "message", "fields?" } }`.
- أخطاء التحقق تعيد `fields` بأسماء الحقول ورسائل عربية.
- الأخطاء غير المتوقعة تعيد `500 INTERNAL_ERROR` برسالة عامة، ولا تُسرّب آثار المكدس أو مسارات الملفات أو نصوص SQL إلى العميل.
- التفاصيل الكاملة تُطبع على الخادم فقط (`console.error`).
- لا توجد بيانات اعتماد أو رموز جلسات في أي استجابة أو سجل.

## 11. الأسرار والإعدادات

- لا توجد أسرار مكتوبة في الكود أو في المستودع.
- `backend/.env` مستثنى في `.gitignore`، و`.env.example` يحتوي قيمًا آمنة فقط.
- `SESSION_SECRET` **إلزامي في الإنتاج**؛ الخادم يرفض الإقلاع بدونه.
- في التطوير، إن لم يُضبط، يُولَّد سر عشوائي عند كل تشغيل (تنتهي الجلسات عند إعادة التشغيل).
- كلمة مرور المدير تُقرأ من البيئة أو تُولَّد تلقائيًا، ولا تُكتب في قاعدة البيانات كنص صريح.

### توليد سر جلسة

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

## 13. القيود المعروفة

هذه النسخة مناسبة لموقع مدرسة واحد وحساب إداري واحد. القيود التالية موثّقة صراحةً:

- **لا توجد مصادقة ثنائية (2FA)** ولا استعادة كلمة مرور عبر البريد.
- **دور إداري واحد** بصلاحيات كاملة؛ لا يوجد فصل بين محرر ومدير.
- **لا يوجد سجل تدقيق (audit log)** لتغييرات الإدارة.
- **حدود المعدل في الذاكرة**؛ عند تشغيل أكثر من نسخة خلف موازن تحميل يجب استخدام مخزن مشترك (Redis مثلًا).
- **SQLite** بكاتب واحد؛ مناسب للحجم الحالي، وليس للتوسع الأفقي الكبير.
- **لا رفع مرفقات لطلبات التقديم**؛ رفع الصور مقصور على وسائط الأخبار من لوحة التحكم، ولا يُقبل SVG.
- **لا إشعارات بريدية أو SMS** للمتقدمين؛ الحالة تُدار داخل لوحة التحكم فقط.
- **لا نسخ احتياطي تلقائي** داخل التطبيق؛ يجب جدولته على مستوى الخادم.
- **تصدير CSV** يُبنى في الذاكرة ويقتصر على 5000 سجل لكل تصدير.
- **لا تشفير على مستوى الحقول** داخل قاعدة البيانات؛ الحماية تعتمد على صلاحيات الملف والنظام.
